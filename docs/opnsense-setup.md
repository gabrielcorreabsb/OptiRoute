# OPNsense setup for OptiRoute

## Prerequisites on OPNsense

1. Install the `os-firewall` plugin:
   - Open **System → Firmware → Plugins**.
   - Search for `os-firewall` and click **+** to install.
   - This plugin enables the **Firewall → Automation → Filter** menu and the `/api/firewall/filter/*` REST endpoints.
2. Generate an API key:
   - Open **System → Access → Users**.
   - Select a user with the firewall permissions listed in [`installation.md`](installation.md) (typically an admin or a dedicated OptiRoute user).
   - Scroll to **API keys** and click **+**.
   - The browser downloads a text file (for example `apikey.txt`) containing:
     ```
     key=xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
     secret=yyyyyyyyyyyyyyyyyyyyyyyyyyyyyyyy
     ```
   - Store this file for importing into OptiRoute.

## Rule structure on OPNsense

Every rule generated by OptiRoute is created inside the `OptiRoute` category on the LAN interface.

### Naming and description format

Rules use the `Description` field to persist the metadata that identifies the application across multiple PCs.

| Type | Description format | Source | Destination | Gateway |
| --- | --- | --- | --- | --- |
| DEFAULT | `OPTIROUTE\|DEFAULT\|<exe>\|<dscp>\|<appId>\|v=1` | `lan net` (or `any`) | `! (self)` | Default WAN |
| OVERRIDE | `OPTIROUTE\|OVERRIDE\|<exe>\|<dscp>\|<sourceIp>\|<appId>\|v=1` | `<PC IP>` | `! (self)` | Custom WAN |

### Protecting local services

OptiRoute configures every rule with:

- `destination_net`: `(self)`
- `destination_not`: `1`

This prevents games and other applications from having their DNS or local-service traffic redirected to the external WAN. For example, DNS queries from a game to the OPNsense Unbound resolver at `10.0.0.1` would otherwise leave through the external interface and fail. The `! (self)` negation keeps traffic to local firewall services intact.

### ToS and DSCP mapping

OPNsense manipulates the DSCP field through the ToS byte in hexadecimal. The relationship is:

```
ToS = DSCP << 2 = DSCP × 4
```

For example, DSCP 33 → ToS `0x84` (132), DSCP 34 → ToS `0x88` (136), DSCP 35 → ToS `0x8C` (140). The `OpnsenseClient` formats and sends both `dscp` and `tos` automatically. The full DSCP/ToS table, including reserved classes and Wireshark filters, is in [`dscp-profiles.md`](dscp-profiles.md).

## Rule ordering on the LAN interface

OPNsense evaluates rules top to bottom (first match wins). `RuleOrderManager` arranges the list as follows so that local overrides work and the user's own rules stay active:

```
1. System rules and the user's custom rules at the top of the LAN
2. OptiRoute OVERRIDE rules (per PC)
3. OptiRoute DEFAULT rules (for the whole LAN)
4. The user's anchor rule (for example LAN LOADBALANCE / General Outbound)
5. Remaining rules and default blocks
```

OptiRoute never moves or deletes rules outside the `OptiRoute` category.

## Validating traffic

### Packet capture from the OPNsense UI

1. Open **Interfaces → Diagnostics → Packet Capture**.
2. Select the **LAN** interface.
3. Enable promiscuous mode.
4. Click **Start** and generate traffic from the application under test.
5. Click **Stop** and download the `.pcap` file.
6. Open it in Wireshark with the filter:

   ```
   ip.dsfield.dscp == 33
   ```

   The *Differentiated Services Field* will show `DSCP 33 (0x21)` and ToS `0x84`.

7. Capture on the expected egress WAN interface (for example `WAN2`) to confirm traffic for that IP and port is flowing through that link.

### Packet capture over SSH

Connect to OPNsense over SSH:

```bash
tcpdump -ni igb1 "ip and (ip[1] & 0xfc) >> 2 == 33" -vv
```

The expression `(ip[1] & 0xfc) >> 2 == 33` extracts the DSCP value from the ToS byte of each IPv4 packet.
