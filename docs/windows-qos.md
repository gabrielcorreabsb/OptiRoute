# Windows QoS — How OptiRoute Uses It

## 1. Policy-based QoS on Windows

Windows includes a native Quality of Service subsystem managed through the `NetQoS` PowerShell module. It intercepts traffic generated by any application at the network driver layer and marks the IP headers with a **DSCP** (Differentiated Services Code Point) value before the packet is transmitted by the network adapter.

OptiRoute uses only the combination of:

- `AppPathNameMatchCondition`: the executable name (for example `bf6.exe`, `discord.exe`).
- `DSCPAction`: the DSCP value assigned to the process (for example `33`).

## 2. PowerShell cmdlets

### 2.1 Create or update a policy

```powershell
New-NetQosPolicy `
    -Name "OptiRoute-bf6" `
    -AppPathNameMatchCondition "bf6.exe" `
    -DSCPAction 33 `
    -NetworkProfile All
```

| Parameter | Example value | Description |
| --- | --- | --- |
| `-Name` | `OptiRoute-bf6` | Unique identifier with the protected `OptiRoute-` prefix |
| `-AppPathNameMatchCondition` | `bf6.exe` | Executable name, without the full path |
| `-DSCPAction` | `33` | DSCP code (0 to 63) |
| `-NetworkProfile` | `All` | Applies to all network profiles (Domain, Private, Public) |

### 2.2 Inspect local policies

OptiRoute reads both the DSCP value and the policy metadata (`Owner` and `PolicyStore`):

```powershell
Get-NetQosPolicy -ErrorAction SilentlyContinue |
    Where-Object { $_.Name -like 'OptiRoute-*' } |
    Select-Object Name, AppPathNameMatchCondition, AppPathName, DSCPAction, DSCPValue, Owner, PolicyStore |
    ConvertTo-Json -Compress
```

### 2.3 Remove a policy safely

```powershell
Remove-NetQosPolicy -Name "OptiRoute-bf6" -Confirm:$false -ErrorAction SilentlyContinue
```

When a policy was created in a specific store (for example `ActiveStore` or a machine GPO), OptiRoute respects the corresponding `-PolicyStore` parameter.

## 3. Safety rules for orphan policies (`LocalOnly`)

OptiRoute follows three strict rules to avoid interfering with the user's own configuration:

1. Strict prefix filter. OptiRoute only inspects, modifies, or removes policies whose name begins with `OptiRoute-`. System policies (such as QoS for Teams audio or domain policies) are ignored entirely.
2. No silent deletion of orphan policies. If a `OptiRoute-*` policy exists on Windows but is not registered on OPNsense (for example after manual testing or after another user removed the global rule on the firewall), OptiRoute never deletes it automatically. Instead, the application is classified as `Local only` and the UI exposes explicit actions:
   - `Remove from Windows`: deletes the local policy through PowerShell.
   - `Register on OPNsense`: promotes the application to the firewall with DSCP collision detection.
3. Automatic UAC elevation. Creating or removing Windows network policies requires Administrator privileges. `OptiRoute.exe` ships an `app.manifest` configured with `requireAdministrator`, which prompts the user for elevation as soon as the application starts.

## 4. Persistence and execution details

- Registry persistence. Policies created by OptiRoute without `-PolicyStore ActiveStore` are persisted in the Windows registry at:
  ```
  HKLM\SOFTWARE\Policies\Microsoft\Windows\QoS
  ```
  This means the policies stay active across reboots and remain in place after OptiRoute is closed.
- Reliable execution without quoting pitfalls. `WindowsQosManager` writes the PowerShell commands to a temporary, cryptographically random `.ps1` file and runs it through `powershell.exe -NoProfile -NonInteractive -ExecutionPolicy Bypass -File "<temp>.ps1"`. The script file avoids the quoting failures that are common when arguments are passed directly on the command line.
